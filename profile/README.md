<p>接口调不通的时候，报错信息往往只有一行，指向的却可能是完全不同的三层：客户端连接池、代理网关、上游出口。不先分层就动手改参数，最常见的结局是把重试次数调大、把超时调长，问题暂时看不见了，代价是故障时排队更长、恢复更慢。这篇按故障树的方式写：先给出三个典型现象和对应的首查项，再逐个展开连接池、重试、限流三处的成因与参数，最后给一份可以直接抄用的最小配置骨架，以及验证它是否生效的办法。</p>

<h2>一、从三个现象倒推：先分清是谁的问题</h2>
<p>三个现象值得记住：请求卡住不动、报错集中在某一类状态码、以及使用一段时间后才开始失败。它们分别指向资源耗尽、上游限流、以及连接复用失效，排查顺序完全不同。</p>
<h3>现象一：前几十个请求正常，之后集体变慢</h3>
<p>这是典型的池子被占满。新请求在等一条空闲连接，等到超时。用 <code>py-spy dump</code> 或打点日志看线程栈，会看到大量线程停在取连接这一步，而不是停在网络读写。</p>
<h3>现象二：错误集中在 429 或 5xx</h3>
<p>429 是对方明确告诉你超了配速，5xx 是对方或中间环节出错。两者混在一起处理是常见错误：对 429 该退避等待，对 5xx 该换出口或快速失败，混着做会让两种情况都变糟。</p>
<h3>现象三：跑一段时间后延迟突然抬高</h3>
<p>多半是长连接被中间设备回收，而客户端还在复用。表现为每隔固定时间出现一批慢请求，周期与设备的空闲回收时间吻合，常见值是六十秒或七十五秒。</p>

<h2>二、连接池耗尽：症状、成因与参数</h2>
<p>池子耗尽的根因通常不是池太小，而是连接被长时间占着不还。读取超时设得过长、响应体没有读完、异常路径没有释放，三者都会让连接一直挂着。</p>

<h3>先确认是不是池的问题</h3>
<p>日志里出现 <code>Connection pool is full, discarding connection</code>，或者 httpx 抛 <code>PoolTimeout</code>，基本可以定位。此时看两个数：池上限和同时进行的请求数，前者小于后者就会排队。</p>
<h3>池大小按并发而不是按总量定</h3>
<p>合理的池上限略高于业务峰值并发，留一到两成余量即可。设成几百并不会更快，因为出口侧的并发限制才是真正的瓶颈，客户端只是把排队从池里挪到了网络里。</p>
<h3>把归还路径补齐</h3>
<p>用上下文管理器确保异常时也归还连接，响应体务必读完或显式关闭。流式响应不读完就丢弃，是连接泄漏最常见的来源，跑几小时就能把池吃干。</p>

<h2>三、重试风暴：为什么越重试越慢</h2>
<p>重试是把偶发失败转成成功的手段，但当失败是系统性的，重试会把请求量成倍放大。三个客户端同时重试三次，等于给已经过载的上游又加了九倍压力，恢复时间被自己拖长。</p>
<h3>指数退避必须带抖动</h3>
<p>固定间隔的重试会让所有客户端在同一时刻再次冲上来。退避基数取零点五秒、指数增长、叠加随机抖动，能把重试打散。没有抖动的退避，本质上只是把尖峰推迟了几秒。</p>
<h3>只对可重试的错误重试</h3>
<p>连接超时、连接被重置、429、502、503、504 可以重试；400、401、403、404 重试没有意义，只会浪费配额。把不可重试的错误也塞进重试列表，是很多客户端默认配置里的坑。</p>
<h3>加熔断，别无限坚持</h3>
<p>连续失败达到阈值就短暂停止向该出口发请求，隔一段时间放一个探测请求试探。没有熔断的重试，会在出口已经不可用时持续打满，拖慢整个调用链。</p>

<h2>四、并发限流：429 与 5xx 该分开处理</h2>
<p>把两类错误分开，是为了让处置动作对症。429 说明你发太快，需要降速；5xx 说明对面或链路有问题，需要换路或等待。混在一起统一重试，等于对限流继续加压。</p>
<h3>429 优先读 Retry-After</h3>
<p>响应头里带 Retry-After 时按其秒数等待，比自己拍一个退避值更准。没有该头时，按最近一分钟的成功速率回退一半，逐步试探恢复点，避免一放就再次触发。</p>
<h3>5xx 先看是不是单条出口</h3>
<p>如果 5xx 集中在某一条出口，说明该出口的链路或上游有问题，直接摘除即可；如果所有出口同时 5xx，更可能是目标服务侧波动，此时应降低并发而不是换线。</p>
<h3>给自己也设一道闸</h3>
<p>客户端按出口维护一个令牌桶，速率略低于合同并发对应的上限。这道闸的作用不是提速，而是让流量形状可预测，遇到突发时排队而不是雪崩。</p>

<h2>五、一份最小可用的配置骨架</h2>
<p>下面这套参数不是最优解，但是一个能跑通、能观测、能回滚的起点。上线后按实际数据微调，比一开始追求精细更有意义。</p>
<h3>连接与超时</h3>
<p>连接池上限五十、保活连接二十、连接超时五秒、读取超时六十秒、保活时间四十五秒。保活时间要短于中间设备的空闲回收时间，否则复用到的是已被对端关闭的连接。</p>
<h3>重试与熔断</h3>
<p>总重试三次、退避基数零点五秒、只对指定状态码重试、尊重 Retry-After；熔断阈值设为连续十次失败，半开探测间隔三十秒。参数写成配置项，不要硬编码在业务代码里。</p>

<h2>常见问答</h2>
<h3>重试次数设多少比较合适？</h3>
<p>答：两到三次是常见区间。次数太少覆盖不到瞬时抖动，太多会在系统性故障时放大流量。配合退避和熔断使用，效果比单纯提高次数更好。</p>
<h3>为什么本地测试正常，上线后才出现池耗尽？</h3>
<p>答：本地并发低、响应快，连接很快归还；上线后并发升高、响应变长，连接占用时间被拉长，池子就被占满。这类问题只在真实负载下暴露，压测时要按生产并发跑。</p>
<h3>换出口算不算一种重试？</h3>
<p>答：算，但要单独计数。换出口重试会增加地址切换频率，频率过高本身就是一个异常信号。建议给换出口重试单独设一个上限，超过就停下来报警而不是继续换。</p>
<h3>代理网关自己会重试，客户端还要重试吗？</h3>
<p>答：需要，但层次要错开。网关侧重试适合处理链路抖动，客户端重试适合处理端到端失败。两层都设三次会变成九次放大，实际配置时把总次数当成一个预算来分配。</p>
